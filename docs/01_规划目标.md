## 2. 范围

### 做
- 当前执行与验收仍在仿真；按 Gemini 335 官方几何和真机项目手眼参数建模，为后续实机减少差异

## 3. 技术选型与理由

| 选型 | 理由 |
|---|---|
| **ROS 2 Humble** | 任务指定；系统已装，不改环境 |
| **Gazebo Classic 11** | 已装且与 `gazebo_ros2_control` 配套；能真实体现夹爪开合与抓取 |
| **MoveIt 2.5.10 + MTC 0.1.3** | 任务书点名 MTC；系统已装；**MTC 0.1.3 仅 C++**，故任务节点必须 C++ |
| **MTC 规划 + `MoveGroupInterface::execute()` 执行** | 规避 MTC 0.1.3 的 `execute()` 需要外部 `execute_task_solution` action server 的问题（官方实现在未安装的 apt 包里，我们不改环境） |
| **全 C++ 节点** | 入门任务，遵循传统 ROS 2 C++ 写法；Python 用于 launch、配置生成及验证工具 |
| **OpenCV 颜色阈值** | 依赖齐备（cv_bridge 3.2.1 / OpenCV 4.5.4）；不引入深度学习 |

## 4. 关键设计决策

### D1 · 夹爪控制：单 JTC 同控 `joint7` + `joint8`
- **理由**：两关节镜像，单控一个需要额外 Python 节点镜像（官方 `joint8_ctrl.py` 方案，还缺可执行位）。
- **做法**：一个 `JointTrajectoryController` 同时含两关节，MTC 直接下发对称指令。
- **取值**：全开 `(0.035, −0.035)`；全闭 `(0.0005, −0.0005)`（留 1 mm 间隙避免两指网格原点重合自碰撞）。

### D2 · MTC 的 `ik_frame` 用 `gripper_base`
- **理由**：`link7` 会随夹爪开合移动 35 mm，用它做 IK 帧会导致闭合时目标漂移。
- **配套**：仿真抓取 TCP 使用法兰 +Z 方向 0.132 m，来自当前碰撞指形与桌面净空计算，是真实抓取前需复核的设计值；不是实机标定的工具中心。

### D3 · 视觉使用腕部 RGB-D 相机
- **参数依据**：Gemini 335 USB，RGB/原生深度 640×480/15 fps，RGB 4:3 标称视场 70°×55°。link6→RGB optical 使用 toy_pick_ws 保存的完整手眼矩阵；外壳变换由矩阵和官方光心偏移反推。RGB 与深度光学系独立，C++ D2C 后使用 RGB 光学系定位。详见 [相机配置与限制](gemini335_20261001/README.md)。
- **观测约束**：RGB-D 按相同时间戳配对，使用图像时刻 TF；相机静稳至少 0.4 s，50 mm 水平方块顶面通过尺寸、平面和覆盖率验证，才能输出坐标。同色料盒以三维取料区与几何规则排除。
- **场景确认**：首次位置/真实位移需连续至少 3 帧确认；运动、遮挡和断流保留历史位置并显式失效。任务触发检查 `/classify/scene_ready`，返回观察姿态重新检测后才使用坐标。详见 [视觉运动误差修复与验收](perception_motion_20260930/README.md)。

### D4 · 使用 `FixedState` + `MoveTo` + `ModifyPlanningScene` 构建 MTC 流水线
- **理由**：物块中心已经由稳定视觉确认；`MoveTo` 直接接收带 TCP 的位姿并求逆解，省去额外生成器。接近/抬升/下降使用全程碰撞检查的 CartesianPath，搬运使用 OMPL。
- **姿态约束**：保留用户后移布局。垂直搬运在较高/较远位置受 joint5 限位限制，实际抓取/抬升相对垂直方向倾斜 30°，搬运/放盒改用 45°；夹取点 TCP 与实际手指碰撞几何匹配。Cartesian 步长 3 mm、最小完成比例 1.0、相对关节跳变阈值 10，保留碰撞检查。
- **执行依据**：MTC 子轨迹和附着/脱离场景差分逐段执行，执行后独立核对 Gazebo 抬升、入盒及绿块位移；完整验证已通过。双指侧面持续接触 50 ms 后建立物理固定约束，张开即释放。这是理想夹持近似，不能替代实机力/摩擦验收。

### D5 · 机器人描述以官方 `piper_ros@humble` 为准，只借用 `agx_arm_sim` 的 world/launch/摩擦写法
- **理由**：agx_arm_sim 的夹爪 URDF（`gripper_joint1/2`）与真实松灵 `joint7/8` 不同，不能直接用。

### D6 · 抓取/放置位姿由视觉+几何计算，但**放在料盒的位姿来自配置**
- **理由**：料盒位置是场景固定设施，属于"环境已知参数"，不是被操作对象。物块位姿才是必须视觉获取的。

## 5. 系统架构

以下系统已实现。自动任务读取已确认视觉坐标及规划场景料盒几何，使用 MTC 规划、控制器执行，并独立验证实际物块运动。

```
┌────────────────────────── Gazebo Classic ──────────────────────────┐
│  world: 桌面 + 红/蓝/绿方块 + 红/蓝料盒                           │
│  robot: piper + 腕部 RGB-D + gazebo_ros2_control                 │
└───────────────────────────────────────────────────────────────────┘
        │ /camera/{color/image_raw,depth/image_raw,color/camera_info}
        │ /tf  /joint_states
        ▼
┌──────────────── classify_perception (C++) ────────────────────────┐
│ HSV 轮廓 + 深度 + 内参 → camera_color_optical_frame 三维点             │
│ TF → base_link；用桌面取料区域排除同色料盒，输出红/绿/蓝检测     │
└───────────────────────────────────────────────────────────────────┘
        │ /classify/detections
        ▼
┌──────────────────── classify_scene_bridge (C++) ─────────────────┐
│ 固定桌子/料盒 + 视觉定位方块 → MoveIt PlanningScene / RViz      │
└───────────────────────────────────────────────────────────────────┘
        │ 规划场景
        ▼
┌────────────────────── classify_task (C++, MTC) ───────────────────┐
│ 任务指令 → 红块抓放 → 蓝块抓放 → 完成数量 1/2、2/2               │
│ MTC 规划抓取与放置；执行时核对 Gazebo 实际物块位姿和夹爪状态     │
│ 绿块不进入抓取序列，始终留在桌面                                  │
└───────────────────────────────────────────────────────────────────┘
        │ /classify/status  /classify/result  /classify/start
        ▼
   move_group ── FollowJointTrajectory ── piper_arm_controller (6 关节)
                                        └ piper_gripper_controller (j7,j8)
```

### 6.1 包命名规范：`classify_` 前缀（强制）

本机已存在**两个已构建的 ROS 2 工作空间**（`piper_ros` 22 个包、`ruikang_sim`），其中 `piper_ros` 已把
`piper_description` / `piper_moveit_config` / `piper_gazebo` / `piper_msgs` / `piper` 等注册进 ament index。

因此本工作空间**所有包一律加 `classify_` 前缀**，避免：
1. colcon 同名覆盖警告
2. `package://<pkg>/meshes/*` 解析到错误工作空间（会加载到别的 URDF 的网格，极难排查）

**URDF 内部**（link / joint 名称）**保持官方命名** `base_link` / `link1..8` / `joint1..8`，
因为官方文档与 MTC/SRDF 参考资料均以此为准，且这些名字只在 URDF 内部解析。

## 2026-10-01 · 仿真与真机参数对齐原则

传感器参数集中在 gemini335.yaml；world 是固定场景几何的唯一来源，workcell.yaml 是检测和场景桥共用的取料配置。保留用户后移的 x=0.40/0.52 布局。已支持设备坐标名称和可配置 RGB-D 时间容差，但实际相机未接入，设备 K/D/光学间外参及手眼残差未测量；不虚构噪声、不把标称值标作设备实测。真实视场下依靠观察姿态取得完整顶面，运动或视野不足时沿用已有过期保护。当前实现为完整仿真分拣基线，S5/S6 已通过实体闭环；实机力控、真实 TCP 与单位设备参数仍需独立验证。

## 2026-10-01 · 启动/停止所有权修正

完整启动的进程组通过 CLASSIFY_WS_ROOT/ROS_LOG_DIR 标识；生命周期锁串行化启动与停止。即使 launch 已退出或 PID 文件缺失，stop 仍清理拥有的残留组；旧 wrapper 的退出清理使用 expected-pid，只操作自身启动。停止等待所有成员退出后才允许新启动。`reset_classify.sh` 统一停止并重新加载初始 world，默认不自动执行任务。见 [重置验证](reset_20261001/README.md)。

## 2026-10-02 · S9 同色多块设计（已完成）

新增独立生成的五块场景：两红、两蓝、一绿；绿块保持原位。视觉逐轮廓输出完整顶面和模 90° 的方块 yaw，场景桥按颜色和空间连续性一对一关联，分配持续 ID；遮挡、歧义和未确认位置不用于抓取。任务从确认场景枚举目标，不读取 Gazebo 取料坐标；预期件数作为场景任务清单检查，防止漏检仍开始。

料盒容量由实际底板和四壁的内边界计算，使用带边距的独立槽位；容量不足在运动前拒绝。放置后检查完整方块在盒内、与已放件不重叠，并同步实际姿态。仿真模型名和视觉 ID 不假定相同：双指实际接触后才绑定物理模型，仅用于执行验证。保持基线世界、官方相机视场、手眼参数和失败/取消重置规则。完成后回归基线与五块实际抓放，并保存证据；本阶段仍非实机接触力和标定验收。

S9 布局实测修订：近排新增块曾被下沿裁切，移入视野后又占用邻件的张开夹爪空间，均在运动前被拒绝。最终用 x≈0.40/0.50 两排布局，取料 X 上限扩至 0.55 m（覆盖旋转后完整顶面）；盒内方块高于桌面顶面模型，仍由高度/面积规则排除。机械臂 HOME、相机视场/安装、基线 world 和绿块原位不变。新增模型名故意与视觉出生编号顺序不同，用实际接触后的绑定验证身份独立性。
