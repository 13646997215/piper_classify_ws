## 3. 两个关键实测结论

### 结论①：官方 URDF 与 toy_pick_ws 的运动学完全一致，只是命名不同

我做了逐项 diff（去掉 `piper_` 前缀后对比 `origin` / `axis` / `limit` / `parent` / `child`），结果**完全一致**：

|      | 官方 piper_ros@humble | toy_pick_ws                     |
| ---- | ------------------- | ------------------------------- |
| 底座   | `base_link`         | `piper_base_link`               |
| 手臂   | `link1` ~ `link6`   | `piper_link1` ~ `piper_link6`   |

**为什么重要**：之前调研 toy_pick_ws 得到的运动学数据（关节限位、TCP 偏移 0.135m、夹爪镜像关系）**可以放心用于官方 URDF**，不需要重算。

**决定**：本项目**采用官方命名**，因为 MTC / SRDF / 官方 MoveIt 配置的参考资料全部以官方命名为准。

### 结论②：官方 gazebo xacro 有一个致命钳位问题（实测确认 8 处）

```xml
<!-- piper_description_gazebo.xacro，8 个关节各一处 -->
<joint name="joint2">
    <command_interface name="position">
        <param name="min">-1</param>
        <param name="max">1</param>
    </command_interface>
```

`gazebo_ros2_control` 会**严格钳制**写入值。后果：

- `piper_joint2` 真实范围 `0 ~ 3.14 rad`，被钳到 `0 ~ 1 rad`（57°）
- **机械臂根本抬不起来**，完全无法完成抓放

同时它还硬引用 `$(find piper_gazebo)/config/ros2_controllers.yaml`——`piper_gazebo` 是另一个包，我们不建，**照抄必然报错**。

**解决**：照抄 `agx_arm_sim` 的干净模板，它这两点都做对了：

```xml
<command_interface name="position"/>          <!-- 无钳位 -->
...
<parameters>${controllers_file}</parameters>    <!-- 参数传入，无跨包硬依赖 -->
```

## 5. 踩的坑

**坑：`set -u` 与 ROS setup 脚本冲突**
`check_env.sh` 最初写了 `set -uo pipefail`，结果脚本在 `source /opt/ros/humble/setup.bash` 处直接失败退出，什么都没输出。

## 4. URDF 的 3 处修正

修正由 `scripts/tools/upgrade_urdf.py` 自动完成，**脚本保留在仓库里以便追溯和复现**。

### 4.1 碰撞体：mesh → box（性能关键）

**问题**：官方 URDF 的 10 个 `<collision>` 全部直接引用 STL 网格。Gazebo 的 ODE 物理引擎对 mesh 碰撞体支持很差（需三角化 + BVH），其中 `link2.STL` 有 **73166 个三角面 / 3.6 MB**，会拖垮物理步进。

**做法**：每个碰撞体换成包围盒内缩的 box。

```
inset = min(3mm, 8% × 该连杆最小边长)
```

# S1 补充 · 首次运行失败与修复

## 1. 现象

用户运行后截图反馈：**Joint State Publisher 窗口里只有 `Randomize` / `Center` 两个按钮，没有任何关节滑块；RViz 窗口也没出现。**

## 2. 诊断

我复现了一次并抓日志。表面现象是"滑块没有"，但**根因是更严重的 rsp 崩溃**：

```text
[robot_state_publisher-1] Error:   Error document empty.
[robot_state_publisher-1] Failed to parse robot description using: urdf_xml_parser/URDFXMLParser
[robot_state_publisher-1] terminate called after throwing an instance of 'std::runtime_error'
```

因果链：

```
display.launch.py 把 URDF 的「文件路径」当参数值传出去
        ↓
robot_state_publisher 拿路径字符串去当 XML 解析 → "Error document empty"

        ↓

```

**"滑块空白"只是表象，真正的错误是 robot_state_publisher 崩了。**

## 3. 两个 Bug

### Bug ①（主因）：传了路径而不是 URDF 内容

原来的写法：

```python
parameters=[{
    'robot_description': ParameterValue(
        os.path.join(pkg_share, 'urdf', 'xxx.urdf'),
        value_type=str),
}]
```

`robot_state_publisher` 的 `robot_description` 参数值必须是 **URDF 的 XML 文本本身**，不是路径。

正确写法（本项目是纯 URDF，直接读文件）：

```python
with open(os.path.join(pkg_share, 'urdf', 'piper.urdf')) as f:
    robot_description = {'robot_description': f.read()}
```

> 补充知识：如果模型是 `.xacro`，官方模板的做法是 `Command(['xacro ', path])`
> —— 让 xacro 进程执行、拿它的 stdout 作为参数值。
> 我最初误以为 `ParameterValue(path, value_type=str)` 等价于"告诉节点去哪读文件"，这是错的。

### Bug ②（我自己 `sed` 批量替换造成的）：URDF 文件名写错

把包名从 `piper_description` 改成 `classify_description` 时用 `sed` 全局替换，
把 launch 文件里的 URDF 文件名也一起改了：

```

实际文件名  : 'piper.urdf'
```

这个 Bug 被 Bug ① 掩盖了（因为传的是路径，节点根本没去打开那个文件），修 Bug ① 时才暴露，一并修正。

**教训**：批量 `sed` 替换包名时，必须把"包名"和"文件名前缀"区分开。

### 关于你说的「两个关节数值一样」

需要纠正一个细节。我用 FK 验证了运动方向：

```text
joint7 轴在 gripper_base 系 = (0, -1, 0)   j7 增大 → 手指向 -Y 移
joint8 轴在 gripper_base 系 = (0, +1, 0)   j8 增大 → 手指向 +Y 移
                                  → 正方向相反
```

| j7        | j8         | 开口       | 含义         |
| --------- | ---------- | -------- | ---------- |
| 0         | 0          | 0mm      | 全闭         |
| 0.035     | 0          | 35mm     | ← 你看到的"半开" |
| 0         | −0.035     | 35mm     | 同上         |
| **0.035** | **−0.035** | **70mm** | ✅ 正确全开     |

**正确关系是 `joint8 = -joint7`（等值反号），不是同号。**
若强行同号（都取 +0.0175），两指会挤到同一侧，开口变 0mm，夹爪彻底错乱。

我实测验证过：发 `(0.035, -0.035)` 后实际到达 `joint7=+0.0345, joint8=-0.0355`，

## 4. 踩到的 6 个坑

### 坑① xacro 宏从未被调用 → 整个 ros2_control 块消失

`<xacro:macro>` 只是**定义**，不写调用就不会出现在展开结果里。
症状极具迷惑性：xacro 成功、不报错、Gazebo 正常生成实体，但**没有 `/controller_manager`**。

```text
$ grep -c '<ros2_control' 展开结果
0                    ← 宏根本没展开
```

修复：在文件末尾加 `<xacro:piper_ros2_control .../>`。

### 坑② launch 把 URDF 当 YAML 解析

```text
[ERROR] Caught exception in launch: Unable to parse the value of parameter
        robot_description as yaml. If the parameter is meant to be a string,
        try wrapping it in launch_ros.parameter_descriptions.ParameterValue
        (value, value_type=str)
```

修复：`ParameterValue(内容, value_type=str)`。
这与 S1 的 bug 是同一类错误（我 S1 刚犯过，这次又犯了一次）。

### 坑③ ★ rcl_parse_arguments 把 URDF 当 YAML 解析（最隐蔽）

`gazebo_ros2_control` 源码里有这么一段：

```cpp
std::string rb_arg = std::string("robot_description:=") + urdf_string;
arguments.push_back(RCL_PARAM_FLAG);
arguments.push_back(rb_arg);
rcl_parse_arguments(...)
```

**整个 URDF 被拼成一个命令行参数**交给 rcl，而 rcl 按 YAML 解析该值。

我写了 C 程序直接复现 `rcl_parse_arguments`，二分定位：

```text
  注释含 "a: b"（冒号+空格）  → FAIL   ← 真凶
  注释含 "a:b"（冒号无空格）  → PASS
  注释含 "ab"                → PASS
  注释含 "x = 1"            → PASS
  删除所有 XML 注释           → PASS
```

**任何 XML 注释里的「冒号+空格」都会被 YAML 误认成键值分隔符。**
连 xacro 自动生成的头注释也含冒号：
`This document was autogenerated by xacro from <path>`。

我最初误判为「非 ASCII 字符问题」（因为官方两个 xacro 的非 ASCII 字节数都是 0），
改掉全部中文后**错误依旧**，才通过 C 程序复现找到真因。

修复：`sed`/正则剥离所有注释后再用。
注意我第一次用 `sed '/<!--/,/-->/d'` 也失败了——sed 的范围匹配遇到注释正文里的双连字符会提前结束，
把注释之后的真实标签（如 `<gazebo>` 开标签）一起删掉，产出标签不配对的 URDF。
最终改用 Python 非贪婪正则 `re.sub(r'<!--.*?-->', '', text, flags=re.S)`。

### 坑④ 我砍掉的 `robot_param_node` 标签根本没用

源码显示：

```cpp
if (sdf->HasElement("robot_param_node")) { ... } else {
    robot_description_node_ = "robot_state_publisher";  // 默认值
}
```

**不写这个标签，默认值就是 `robot_state_publisher`**，删了等于没删。
插件总是从 rsp 节点取 URDF，这是它的固有设计。

### 坑⑤ sed 范围匹配误删真实标签

见坑③后半段。表现是生成的 URDF 缺 `<gazebo>` 开标签却留着 `</gazebo>`，
报 `mismatched tag: line 346`。改用 Python 正则。

### 坑⑥ ★ 5 个 robot_state_publisher 同时发布 /robot_description

这一条最阴，因为**日志里完全看不出问题**：

```text
$ ros2 node list | grep robot_state | wc -l
5
$ ros2 topic info /robot_description
Publisher count: 5
```

前几次测试的 launch 进程没被完全清理，5 个 rsp 抢同一个话题。
`spawn_entity` 随机抓到其中一个（带注释的旧版本），于是插件报 `parser error`。
**我一直在追一个由"环境不干净"造成的假象。**

清理方式也踩了坑：`pkill -f "ros2 launch ..."` 的模式会**匹配到执行它的 shell 自身**，
导致命令自杀（日志里直接出现 `Killed by SIGTERM`）。
正确做法是用 `ps -eo pid,comm` 精确匹配进程名，不用 `-f` 匹配完整命令行。

### build_urdf.sh 的设计

把去注释后的 URDF 作为**构建期就存在的文件**提交进包里，launch 在构建期直接读取。
这样避开了一个死结：需要先跑 `ExecuteProcess` 生成 URDF，但 `FileContent` 和 `Command`
都在**构建 launch 描述时**就求值，早于 ExecuteProcess；`OnProcessExit` 能控制节点启动顺序，
但控制不了参数求值时机。

脚本内置 6 项校验，任何一项不过就不覆盖目标文件：

1. 输出非空
2. XML 可解析
3. 含 `<ros2_control>` 块（证明宏被调用）
4. 含 `libgazebo_ros2_control.so`
5. 8 个 `position` 命令接口
6. **无 min/max 钳位**（官方文件的致命 bug）

### stop_sim.sh 的设计

因坑⑥ 而写。判据用「进程是否还在」而非「ros2 node list」——
daemon 的发现缓存在进程退出后仍保留记录，会造成假警报。

## 2. 料盒穿模：已定位到具体结构错误

位置：`src/description/classify_description/worlds/classify.world:303` 起，两个料盒具有同样的问题。

当前文件把五块板写成同一个 `collision` / `visual` 内的五个 `geometry/box`，每个 `box` 内又放一个 `pose`：

```xml
<collision name="collision">
  <geometry>
    <box>
      <size>0.13 0.13 0.012</size>
      <pose>0 0 0.006 0 0 0</pose>
    </box>
    <!-- 此后还放了四个 box -->
  </geometry>
</collision>
```

**这是错误的复合几何写法。** 每块板需要自己的 `collision` 和 `visual`，各自包含一个几何；板的位姿放在 `collision/pose` 和 `visual/pose`，不能放进 `box`。

用本机安装的 **libsdformat9** 写了独立 C++ 探针。读取现有 world 的结果是：

```text
load_errors=0
bin_red model_pose=0.22 0.42 0.35 0 -0 0 collisions=1 visuals=1
 collision=collision pose=0 0 0 0 -0 0 box=0.13 0.13 0.012
 visual=visual pose=0 0 0 0 -0 0 box=0.13 0.13 0.012
bin_blue model_pose=-0.22 0.42 0.35 0 -0 0 collisions=1 visuals=1
 collision=collision pose=0 0 0 0 -0 0 box=0.13 0.13 0.012
 visual=visual pose=0 0 0 0 -0 0 box=0.13 0.13 0.012
```

解释：两个料盒各只有**一块板的有效几何**，位姿偏移为零；四壁没有成为独立几何。Gazebo 11 的渲染源码同样通过 `GetElement("box")` 取单个 box 的尺寸，并不遍历这些 box 建造五块板。[Gazebo 11 Visual.cc](https://github.com/gazebosim/gazebo/blob/gazebo11/gazebo/rendering/Visual.cc#L442-L450)

料盒模型原点为 z=0.350，板厚 0.012，因此实际板的高度范围为 **[0.344, 0.356]**，下半部分埋入桌面 **6 mm**。之前改四壁的长宽无法解决这个问题，因为渲染本来就没有按预想构造四壁。

证据：[sdf_bins.txt](audit_20260930/sdf_bins.txt)、[sdf_probe.cpp](audit_20260930/sdf_probe.cpp)。本机规范文件 `/usr/share/sdformat9/1.6/box_shape.sdf` 只定义 `size`；`pose` 定义在 `visual.sdf` / `collision.sdf`。

`scripts/tools/check_scene.py:52` 的 `boxes_of()` 会遍历所有 box，并把 `box/pose` 当作有效位姿。它是在计算作者希望存在的五块板，**没有按 Gazebo 消费配置的方式验证**。此次实跑旧脚本，仍然是“全部通过，0 警告”。

## 4. IK 校验的“0 mm / 0°”是误报

`scripts/tools/check_ik.py` 存在三个直接影响结论的问题。

### 4.1 世界坐标被当作基座坐标

FK 从 `base_link` 开始，输入目标却直接使用 world 的 z。基座实际在世界 z=0.347，脚本没有执行 world→base 的坐标变换。

例如红块世界中心为 z=0.375，正确的基座系高度应是 **0.028**；旧脚本在基座系里解 z=0.375，变回世界是 **0.722**。相差整整 **347 mm**。

### 4.2 姿态误差函数在 180° 时也返回零

第 56 行使用旋转矩阵反对称部分：

```python
dw = 0.5 * [Re[2,1]-Re[1,2], Re[0,2]-Re[2,0], Re[1,0]-Re[0,1]]
```

它的模长对应 `sin(theta)`，不是旋转角；在 theta=π 时同样是零。随后把这个模长换算为角度，还会错误显示“0°”。

独立探针重现旧求解器的五点结果，五个点的真实旋转差都是 **180°**，旧残差却接近零。旧 FK 在基座系中的位置残差确实接近零，但它解决的是错误高度的目标。

### 4.3 检查目标与场景分开硬编码

脚本没有读取 world、launch 的 spawn 变换、现行 URDF 和夹爪 TCP 参数；工作点、关节限位和链参数各维护一份。改场景后可能继续校验旧工作点。另外，即使打印“不可达”，脚本也没有失败退出码。

此次用**现行 URDF 解析出的关节链**、正确的高度变换和 `Rotation.as_rotvec()` 重新计算。采用固定目标姿态、多初值有界最小二乘，结果如下：

| 工作点 | 固定 45° 斜抓：最小位置误差 | 垂直向下：最小位置误差 |
|---|---:|---:|
| red_block | < 0.001 mm | < 0.001 mm |
| green_block | < 0.001 mm | < 0.001 mm |
| blue_block | 5.558 mm | < 0.001 mm |
| bin_red | < 0.001 mm | 25.946 mm |
| bin_blue | 8.370 mm | 25.946 mm |

以上只证明：**三个物块的现位置存在满足限位的垂直姿态 IK 解**，因此“只能斜抓、不能垂直抓”的绝对结论不成立。未收敛到精确解的点只是此次搜索未找到精确解，不能据此证明全局无解。料盒目标本身还沿用旧脚本的试验高度，不等于已定义好的放置轨迹。

证据：[kinematics_results.json](audit_20260930/kinematics_results.json)、[kinematics_probe.py](audit_20260930/kinematics_probe.py)。

## 5. 腕部相机存在，但 HOME 视野与光学坐标都不正确

本机解析器确认传感器保留在固定关节合并后的 `link6` 上，位姿与 xacro 一致；历史日志也确实有 camera_info / depth / points 发布记录。因此“腕部相机已挂上”有依据。

但现行 HOME 下计算出的相机状态为：

```text
相机世界位置 ≈ (0.216644, 0.019140, 0.817725)
Gazebo 相机前向（相机 +X）≈ (0.006923, -0.999917, 0.010827)
```

相机几乎水平朝 **-Y**，不是注释中的“沿接近方向向下 45°”。三个物块转换到传感器的前向深度均为负数，约 **-0.287 m**，即位于相机后方。按当前初始姿态一次检测缓存三件的方案，无法看到这些工件。这是基于现行模型和初始姿态的几何计算，尚未对运行时图像验收。

另一个问题：插件写 `frame_name=camera_link`，该 TF 是 Gazebo 相机体坐标（+X 向前），而 RGB-D 反投影/点云按光学坐标（+Z 向前）表达。当前 URDF 没有独立 optical frame，直接用这个 TF 会转错三维坐标。官方插件源码明确采用光学坐标，并要求 URDF 给出体坐标到光学坐标的固定旋转。[Gazebo ROS camera 源码](https://github.com/ros-simulation/gazebo_ros_pkgs/blob/ros2/gazebo_plugins/src/gazebo_ros_camera.cpp#L678-L690)

后续需要：明确安装变换是哪种相机坐标的变换，建立 `camera_optical_frame`，统一消息 frame_id，并定义可以看到三个物块的观察姿态。仿真安装变换已知，不需要为了复刻实机额外安排一次手眼标定实验。
